## 1. 这套软件是做什么的

在**空载台架**上对 2.5T 电驱桥做下线测试。台架只给控制器（MCU）上 12V 低压和 340V 高压，**没有整车**，所以上位机要**冒充整车控制器（VCU）**：

- **发**：每 10 ms 向 MCU 发一帧 `VCU_11`（CAN ID `0x258`），告诉它"使能/不使能、什么模式、目标转速或转矩、什么挡位"。
- **收**：MCU 周期性回报 `0x35A`（母线电压电流、故障）、`0x35B`（转速转矩、使能状态，10 ms 一帧）、`0x35C`（电机/控制器温度）。
- **看**：把反馈实时显示在界面上，画转速转矩曲线，提供原始报文监视。
- **测**：手动控制，或者按"正转 → N 挡缓冲 → 反转 → N 挡缓冲"这样的步骤序列自动循环测试。
- **供电**：通过 PLC 自动给台架接通 / 断开 340 V 高压，并监视 PLC 安全回路（Safe）。
- **保**：急停、越限自动停机、反馈中断看门狗、硬件掉线自动断开、Safe 断开切高压等多层保护。

协议依据仓库根目录的两张表：
- `DFAC_Matrix_11898_CAN_DF_8_AMB2_V1.2_PCAN-0813_MCU.xlsx`（通信矩阵：每个信号在第几位、多长、精度、偏移）
- `DFAC 控制器故障代码-AMB2(2).xlsx`（故障码表）

│                              │  ├─ 10 ms 发送循环 (_tx_loop)                                       │
│                              │  ├─ 5 ms 接收循环 (_rx_loop) + 安全监控 + SSE 广播                  │
│                              │  └─ 循环测试状态机 (_cycle_loop)                                    │
│                              ▼                                                                   │
│                       core/can/codec.py（信号 ⇄ 8 字节）                                           │
│                       core/can/driver.py（ctypes 调 zlgcan.dll，线程池 + 超时）                     │
└──────────────────────────────┼───────────────────────────────────────────────────────────────────┘

关键点：
- **前后端在同一个进程里**。桌面版不是"浏览器 + 服务器"两个程序，而是 PyWebView 开一个窗口，窗口里的网页访问本进程里的 uvicorn 服务器。
- **后端是唯一的"真相来源"**：控制指令、循环测试进度、安全状态都在后端，前端只是显示和发请求。所以前端刷新页面、甚至关掉重开，电机控制都不受影响。
- **AxleManager 是全局单例**：整个进程只有一个，所有 API 都通过它操作硬件。

### 2.2 一次"开启使能"的完整旅程

1. 操作员点"开启使能" → [VcuCommandCard.vue:201](../frontend/src/components/axle/VcuCommandCard.vue#L201) `handleToggleEnable()`，为防飞车同时把目标转矩/转速置 0。
2. → Store [useAxleStore.ts:258](../frontend/src/stores/useAxleStore.ts#L258) `sendCommand()` → [api/axle.ts](../frontend/src/api/axle.ts) `POST /api/v1/axle/command`，body `{"mcu_en_cmd":1,"torque_req":0,"speed_req":0}`。
3. → 后端路由 [axle.py:171](../backend/app/routers/axle.py#L171) → Pydantic 先校验字段范围（不合法直接 422）。
4. → [axle_manager.py:724](../backend/app/services/axle_manager.py#L724) `update_command()`：检查是否在停止中、是否被循环测试占用、是否急停互锁，然后**只修改内存里的 `_command` 对象**，立即返回。
5. → 下一个 10 ms 节拍，[_tx_loop](../backend/app/services/axle_manager.py#L1191) 读 `_command`，Life 计数 +1，调用 [encode_vcu_11](../backend/app/core/can/codec.py#L73) 编成 8 字节，经 [driver.transmit](../backend/app/core/can/driver.py) 交给 `zlgcan.dll` 发上总线。
6. MCU 收到后开始使能，在 `0x35B` 里回报 `MCU_EnSts=1`。

也就是说：**API 只改"想要的状态"，真正发报文的是 10 ms 循环**。这是周期报文系统的通用做法——即使 API 没人调用，VCU_11 也必须持续以 10 ms 发送，否则 MCU 会报"VCU 节点丢失"。

### 2.3 一帧反馈到屏幕的旅程

1. MCU 发 `0x35B` → USBCAN 硬件缓冲。
2. [_rx_loop](../backend/app/services/axle_manager.py#L1299) 每 5 ms 调 `driver.receive()` 批量取出 → [_process_frames](../backend/app/services/axle_manager.py#L1346) 按 ID 分发 → [decode_mcu_motor_2](../backend/app/core/can/codec.py#L198) 解码 → 存入 `self._mcu_2`，记录时间戳。
3. 同一帧立即做越限判定 `_evaluate_safety()`；每轮循环做一次反馈看门狗 `_evaluate_feedback_watchdog()`。
4. 每 50 ms，`_broadcast_telemetry()` 把整个系统快照（`AxleTelemetry`）放进每个 SSE 订阅者的队列。
5. 路由 `_telemetry_event_stream` 从队列取出，序列化成 JSON，按 SSE 格式写给浏览器。
6. 前端 [startSse](../frontend/src/stores/useAxleStore.ts#L178) 的 `EventSource` 收到 → `telemetry.value = data` → Vue 响应式系统自动刷新所有用到它的组件（反馈卡片再做 200 ms 节流）。

## 3. 读代码前需要的基础知识

只讲本项目真正用到的部分。

### 3.1 Python 异步：async / await / 事件循环

后端几乎全是 `async def`。理解它只需要三句话：

- **事件循环**是一个"调度员"，在一个线程里轮流执行很多任务（协程）。
- 任务执行到 `await xxx` 时，如果 `xxx` 需要等待（睡眠、网络、硬件），就**主动让出**，调度员去执行别的任务；等的东西好了再回来继续。
- 因此，10 ms 发送循环、5 ms 接收循环、循环测试计时、HTTP 请求处理可以在**同一个线程**里"同时"进行，而不用开多个线程。

```python
async def _tx_loop(self):
    while self._is_transmitting:
        ...                      # 编码报文
        await self._driver.transmit(...)   # 等硬件时让出
        await asyncio.sleep(剩余时间)        # 睡到下一个 10 ms 节拍时让出
```

**用到的几个工具：**

| 工具 | 作用 | 在本项目中的用途 |
|---|---|---|
| `asyncio.create_task(coro)` | 把协程变成后台任务并立即开始调度 | 启动 TX/RX 循环、循环测试、链路故障处理 |
| `task.cancel()` | 请求取消任务，任务在下一个 `await` 处收到 `CancelledError` | 断开时停止收发循环 |
| `asyncio.Lock()` | 协程间互斥锁 | 保护 `_command` 等共享状态 |
| `asyncio.Event()` | 一个协程等待另一个协程"发信号" | 断开时等待两帧停机帧发完 |
| `asyncio.wait_for(x, timeout)` | 给等待加超时 | 驱动调用超时、停机帧超时 |
| `asyncio.Queue(maxsize)` | 协程间的有界队列 | SSE 推送 |
| `loop.run_in_executor(pool, func)` | 把**阻塞函数**丢到线程池执行，自己 `await` 结果 | 调用 `zlgcan.dll`（C 函数会阻塞） |

> 为什么 DLL 要放线程池？C 函数执行时不会"让出"，如果在事件循环线程里直接调用一个卡住的 `ZCAN_Receive`，整个后端（包括急停 API）都会卡住。放进线程池后，事件循环照常运转。

### 3.2 ctypes：Python 调 C 动态库

[driver.py](../backend/app/core/can/driver.py) 用 `ctypes` 加载 `zlgcan.dll`：

```python
dll = windll.LoadLibrary("zlgcan.dll")
dll.ZCAN_OpenDevice.argtypes = [c_uint, c_uint, c_uint]   # 声明参数类型
dll.ZCAN_OpenDevice.restype = c_void_p                    # 声明返回类型（64 位指针！）
handle = dll.ZCAN_OpenDevice(4, 0, 0)
```

- **必须声明 `restype = c_void_p`**：默认返回值按 32 位 int 处理，64 位句柄会被截断，导致后续调用崩溃。
- C 语言的结构体用 `class X(Structure): _fields_ = [...]` 描述，见 [zlgcan_types.py](../backend/app/core/can/zlgcan_types.py)，字段顺序和类型必须与周立功头文件 `zlgcan.h` 完全一致。
- `byref(obj)` 相当于 C 的 `&obj`（传指针）。

### 3.3 Pydantic：数据校验模型

[schemas/axle.py](../backend/app/schemas/axle.py) 里每个 `class Xxx(BaseModel)` 描述一种 JSON 结构：

```python
class VcuCommandUpdateRequest(BaseModel):
    model_config = ConfigDict(extra="forbid")       # 多传一个未知字段就报错
    speed_req: int | None = Field(default=None, ge=-12000, le=12000)  # 范围约束
```

FastAPI 收到请求时自动用模型校验，不合法直接返回 **422**，代码里不用手写 if 判断。`@model_validator` 用于跨字段校验（例如"N 挡转速必须为 0"）。

### 3.4 FastAPI 的几个概念

- **路由**：`@router.post("/command")` 把一个 URL 绑定到一个函数。
- **依赖注入**：`manager: AxleManagerDep` 参数会自动得到 `AxleManager` 单例（见 [dependencies.py](../backend/app/dependencies.py)），测试时可替换。
- **lifespan**：应用启动/关闭时执行的代码。本项目启动时配置日志，关闭时调用 `manager.shutdown()` 发停机帧、释放 USBCAN（[main.py:37](../backend/app/main.py#L37)）。
- **SSE（Server-Sent Events）**：一个永不结束的 HTTP 响应，服务器不断写入 `event: telemetry\ndata: {...}\n\n`，浏览器用 `EventSource` 接收。比 WebSocket 简单，单向推送足够。

### 3.5 CAN 总线基础

| 概念 | 说明 |
|---|---|
| 报文 ID | 11 位标准帧，如 `0x258`；ID 越小优先级越高 |
| DLC / 数据 | 每帧最多 8 字节数据 |
| 周期报文 | 按固定周期发送，接收方以此判断对方是否在线 |
| 信号 | 8 字节里按位切分出的物理量，由"起始位、长度、精度、偏移"定义 |
| 物理值 ↔ 原始值 | `物理值 = 原始值 × 精度 + 偏移`；反过来 `原始值 = (物理值 − 偏移) / 精度` |
| Motorola（大端）| 多字节信号的**高字节在前**。本项目所有信号都是 Motorola LSB 格式 |
| Life 计数器 | 每帧 +1、0~15 循环的 4 位计数。接收方发现它不变或跳变，就知道发送方卡死或丢帧 |
| 波特率 | 本项目默认 500 kbps，收发双方必须一致 |
| 终端电阻 | 总线两端各 120Ω；缺失会导致发送失败（无应答） |

### 3.6 Vue 3 + Pinia（前端）

- **单文件组件 `.vue`**：`<script setup>`（逻辑）+ `<template>`（HTML）+ 可选样式。
- **响应式**：`ref(x)` 包装一个值，改 `.value` 时用到它的界面自动刷新；`computed(() => ...)` 是自动重算的派生值；`watch(源, 回调)` 在源变化时执行副作用。
- **Pinia Store**：全局共享状态。本项目只有一个 [useAxleStore](../frontend/src/stores/useAxleStore.ts)，所有组件从它读遥测、通过它发请求。
- **Teleport**：把组件的一部分渲染到页面其他位置。页面右上角的状态徽标就是从页面组件"传送"到顶部栏的。
- **shadcn/vue**：组件库，组件源码直接放在 `frontend/src/components/ui/`（可读可改），样式用 Tailwind CSS 类名。

## 5. 后端详解

### 5.1 启动链路

有两种启动方式，最终都调用同一个 [create_app()](../backend/app/main.py#L54)：

| 方式 | 入口 | 特点 |
|---|---|---|
| 开发 | `cd backend && uv run main.py` | uvicorn 监听 8000、代码改动自动重启；前端另开 `pnpm dev`（5173），通过 Vite 代理访问 `/api` |
| 桌面/生产 | `desktop.py`（打包后就是 EXE） | 同一进程托管前端静态文件；随机端口；PyWebView 窗口 |

`create_app()` 做的事：创建 FastAPI → 加 CORS → 挂载 `/api/v1/axle/*` 路由 → 注册 `/health` → 桌面模式下用 `application.frontend(...)` 托管 `static/` 并让未知路径回退到 `index.html`（Vue 路由刷新不 404）。

`lifespan()`：启动时 `configure_logging()`；关闭时 `get_axle_manager().shutdown()`。

### 5.2 CAN 驱动层 `core/can/driver.py`

**职责**：把周立功 C 接口包装成"异步、带超时、不会卡死事件循环"的 Python 方法。

**DLL 定位** `_resolve_dll_path()`：打包环境优先找 PyInstaller 解压目录 `_MEIPASS/zlgcan_x64/zlgcan.dll`，开发环境找 `backend/zlgcan_x64/zlgcan.dll`。加载时还会把 `kerneldlls/` 加入 DLL 搜索路径（周立功的设备子驱动在里面）。

**统一调用入口 `_call(limit_seconds, description, func, *args)`**：

```python
return await asyncio.wait_for(loop.run_in_executor(self._executor, func, *args), timeout=limit_seconds)
```

- 打开/初始化/关闭类调用超时 **5 s**（`_C_CALL_TIMEOUT`），单帧收发超时 **0.5 s**（`_IO_CALL_TIMEOUT`）。
- 超时抛 `CanDriverError("xxx超时（0.5s），硬件可能已断开。")`。
- 局限：超时只能让协程不再等待，**已经进入 C 函数的线程无法被强行终止**。所以线程池开了 6 个线程留余量，并由上层"链路故障检测"在持续异常时主动断开。

**打开通道** `open_channel(channel, baud_rate)`：
1. 从 [BAUDRATE_TIMINGS](../backend/app/core/can/constants.py#L44) 查 SJA1000 控制器的 Timing0/Timing1 寄存器值（如 500k → `0x00, 0x1C`）。
2. 尝试 `ZCAN_SetValue("0/baud_rate")`（新款设备用，老款 USBCAN2 返回失败属正常）。
3. `ZCAN_InitCAN` 填入寄存器值、验收码全通（接收所有 ID）、正常模式。
4. `ZCAN_StartCAN` 启动通道。

**收发**：
- `transmit()` 受 `_tx_lock` 保护，保证多个协程不会同时写硬件；返回 `True/False`（`False` 通常是总线无应答或发送缓冲满）。
- `receive()` 复用预先分配的 ctypes 接收缓冲区（避免每 5 ms 创建大对象），一次最多取 100 帧。

**`UnavailableCanDriver`**（[driver.py:505](../backend/app/core/can/driver.py#L505)）：DLL 加载失败时的"占位驱动"。接口和真驱动一样，但打开设备/收发都抛"CAN 驱动加载失败: 原因"，关闭类操作什么也不做。这样程序仍能启动，界面能显示失败原因，而不是所有接口 500。

**`windows_high_resolution_timer()`**：Windows 默认定时器精度约 15.6 ms，`asyncio.sleep(0.01)` 实际会睡 15~16 ms。调用 `timeBeginPeriod(1)` 把精度提到 1 ms，10 ms 周期才准。

### 5.3 信号编解码 `core/can/codec.py`

纯函数、无副作用，是协议正确性的核心，有独立测试 [test_can_codec.py](../backend/tests/test_can_codec.py)。

#### VCU_11（0x258，上位机 → MCU，10 ms）

| 字节 | 位 | 信号 | 精度/偏移 | 本项目取值 |
|---|---|---|---|---|
| 0–1 | 16 位 | VCU_MotorTorReq 目标转矩 | 0.1 / −3000 Nm | 手动转矩模式时为给定值，否则 0 |
| 2–3 | 16 位 | VCU_MotorSpdReq 目标转速 | 1 / −12000 rpm | 速度模式给定值 |
| 4–5 | 16 位 | VCU_AccPosition 加速踏板 | 0.1 % | **固定 0**（整车信号） |
| 6 | bit0–2 | VCU_MotorWorkModReq 工作模式 | 0 关闭 / 1 转矩 / 3 速度 | |
| 6 | bit3 | VCU_MCUEnCmd 使能 | 0/1 | |
| 6 | bit4 / 5 / 6–7 | 手刹 / 制动 / ABS | | **固定 0**（整车信号） |
| 7 | bit0–2 | VCU_GearSts 挡位 | 1 D / 2 R / 3 N | 台架只用 D/R/N |
| 7 | bit3 | VCU_ActiveDischg 主动放电 | | **固定 0** |
| 7 | bit4–7 | VCU_Life | 0–15 循环 | 每帧 +1 |

**算一遍**：速度模式、使能、D 挡、目标 1000 rpm、Life=5：

```text
转矩 0 Nm   → raw = (0 + 3000) / 0.1 = 30000 = 0x7530 → 字节0=0x75 字节1=0x30
转速 1000   → raw = 1000 + 12000    = 13000 = 0x32C8 → 字节2=0x32 字节3=0xC8
踏板 0      → 字节4=0x00 字节5=0x00
字节6       = 模式3 | (使能1<<3) = 0x03 | 0x08 = 0x0B
字节7       = 挡位1 | (Life5<<4) = 0x01 | 0x50 = 0x51
报文        = 75 30 32 C8 00 00 0B 51
```

所有输入先 `clamp_val` 夹在量程内，防止越界溢出成反向大值。

#### MCU 反馈解码

| 报文 | 周期 | 字节/位 | 信号 | 换算 |
|---|---|---|---|---|
| 0x35A | 100 ms | 0–1 | 母线电压 | ×0.1 V |
| | | 2–3 | 母线电流 | ×0.1 − 1000 A |
| | | 4 / 5 | 故障个数 / 故障代码 | 原值 |
| | | 6 bit0–2 / bit3–6 | 故障等级 / Life_1 | |
| | | 7 bit0–1 | 温度故障等级 | |
| 0x35B | 10 ms | 0–1 | 最大可用转矩 | ×0.1 − 3000 Nm |
| | | 2–3 | 实际转速 | −12000 rpm |
| | | 4–5 | 实际转矩 | ×0.1 − 3000 Nm |
| | | 6 | 放电状态(bit0–1)、工作模式(2–4)、低压(5)、使能(6)、电机过温(7) | |
| | | 7 | 控制器过温(bit0)、驻坡(1)、Life_2(2–5) | |
| 0x35C | 100 ms | 5 / 6 | 电机温度 / 控制器温度 | −40 ℃ |

> 驻坡、放电状态仍按矩阵完整解码（方便将来需要），但台架版本不再上报给界面。

**例**：母线电压显示 21.8 V ⇔ 字节 0–1 为 `00 DA`（218 × 0.1）。这是 MCU 发来的原值，上位机没有换算错误；未上高压时的读数来自 MCU 采样零漂或母线残余电压。

### 5.4 数据模型 `schemas/axle.py`

前后端之间的"合同"，前端 [types/axle.ts](../frontend/src/types/axle.ts) 与之一一对应。最重要的几个：

| 模型 | 用途 |
|---|---|
| [VcuCommandUpdateRequest](../backend/app/schemas/axle.py#L22) | 手动控制请求，只开放转矩、转速、模式、使能、挡位(1–3) |
| [VcuCommandState](../backend/app/schemas/axle.py#L63) | 当前正在发送的控制量 + Life |
| [CycleTestStep / CycleTestStartRequest](../backend/app/schemas/axle.py#L74) | 循环测试步骤；校验"D/R 转速为正、N 挡转速为 0、正反转之间必须有 N 挡缓冲（含跨圈）" |
| [CycleTestStatus](../backend/app/schemas/axle.py#L117) | 循环测试进度（后端维护） |
| [AxleSafetyConfig](../backend/app/schemas/axle.py#L173) | 安全阈值：转速、转矩、温度、反馈超时 |
| [AxleSafetyTrip](../backend/app/schemas/axle.py#L213) | 一次自动停机事件 |
| [AxleTelemetry](../backend/app/schemas/axle.py#L259) | **整个系统快照**，SSE 每次推送的就是它 |

`AxleTelemetry` 中几个容易误解的字段：
- `mcu_2_last_rx_timestamp`：最近一次**成功解码** 0x35B 的时间。前端用它判断数据是否"新鲜"，避免把断线前的旧值当成当前值。
- `link_error`：硬件链路故障导致自动断开的原因，重连成功后清空。
- `bus_warning`：空闲时驱动调用异常（多为控制器未上电，总线无节点应答，USBCAN 反复重发使发送超时），只提示不断开；收发恢复成功后清空。
- `driver_error`：DLL 加载失败原因，`null` 表示驱动正常。
- `recent_frames`：原始报文列表，只有 CAN 页订阅时才携带（数据量大）。

### 5.5 核心：`services/axle_manager.py`

这是全系统最重要的文件（约 1450 行）。建议对照下面的结构阅读。

#### 5.5.1 状态字段（[__init__](../backend/app/services/axle_manager.py#L113)）

| 分组 | 字段 | 说明 |
|---|---|---|
| 硬件 | `_driver`、`_driver_error` | 驱动实例（或占位驱动）及加载失败原因 |
| 连接配置 | `_device_type/_device_index/_channel/_baud_rate` | `_channel=-1` 表示双通道同时收发 |
| 控制 | `_command` | **当前要发的 VCU_11 内容**，所有控制最终都是改它 |
| 反馈 | `_mcu_1/_mcu_2/_mcu_tbox` + 各自 `_last_rx_timestamp` | 最近一次解码结果和时间 |
| 状态 | `_connected`、`_is_transmitting`、`_is_emergency_locked`、`_disconnecting` | |
| 循环测试 | `_cycle_status`、`_cycle_config`、`_cycle_task`、`_cycle_generation` | |
| 安全 | `_safety_config`、`_safety_last_trip`、`_enable_since` | |
| 链路健康 | `_driver_error_streaks`、`_link_error`、`_link_failure_task` | |
| 报文监视 | `_recent_frames`（容量 500 的环形队列） | |
| 推送 | `_subscribers` | SSE 队列集合 |

#### 5.5.2 两把锁

- **`_lock`**：保护上述状态。凡是"读-改-写"共享状态都在 `async with self._lock:` 里完成，避免 10 ms 循环读到改了一半的命令。
- **`_lifecycle_lock`**：串行化"连接 / 断开 / 退出"，防止用户连点两次连接、或连接与自动断开交叉执行时操作同一个硬件句柄。

规则：**持有 `_lock` 时不要等待需要 `_lock` 的任务**，否则死锁。这就是 `_disconnect()` 为什么分三段加锁、在锁外取消并等待收发任务。

#### 5.5.3 连接与断开

[connect()](../backend/app/services/axle_manager.py#L219)：
1. 已连接则先走完整断开流程（等旧任务退出再释放句柄）。
2. `open_device` → 逐个 `open_channel`；任何一步失败都**回滚关闭**已打开的通道和设备，避免句柄泄漏。
3. 置 `_connected=True`，启动 `_tx_loop` 和 `_rx_loop` 两个后台任务。
4. 记事件日志"CAN 已连接"。

[_disconnect()](../backend/app/services/axle_manager.py#L309) 是精心设计的"安全停机"流程：

```text
第 1 段（持锁）：结束循环测试 → 控制量置安全值（不使能/零转矩零转速/N 挡/关闭模式）
               → 标记 _disconnecting，要求 TX 循环发满 2 帧停机帧
第 2 段（不持锁）：最多等 200 ms，等 TX 循环确认两帧停机帧已发出（Life 连续）
第 3 段（持锁）：置未连接、清反馈时间戳 → 在锁外取消并等待 TX/RX 任务退出
第 4 段（持锁）：关闭通道、关闭设备；如果第 2 段没确认到停机帧，关闭前再补发一帧
```

为什么用"让 10 ms 循环自己发停机帧"而不是直接发？因为 Life 计数要连续，MCU 才会认为这是正常的最后几帧；直接插发可能和循环里的帧 Life 重复。

#### 5.5.4 10 ms 发送循环 [_tx_loop](../backend/app/services/axle_manager.py#L1191)

```text
next_tick = 现在
循环:
    持锁：Life+1，读出 _command 各字段（快照）
    编码 → 逐通道 transmit
        异常 → 计入链路异常统计（可能触发自动断开）
        返回 False → 错误计数 +1，限流告警
    成功 → 记入报文监视；若处于停机阶段则累计停机帧
    next_tick += 10 ms
    还没到 → sleep 到 next_tick
    已落后超过一个周期（卡顿过） → next_tick = 现在（重新对齐，不集中补发）
```

"绝对时间推进"（`next_tick += 10ms` 而不是"每次睡 10 ms"）可以消除累积漂移；"落后就重新对齐"避免卡顿恢复后一口气补发几十帧。

#### 5.5.5 5 ms 接收循环 [_rx_loop](../backend/app/services/axle_manager.py#L1299)

每轮：逐通道 `receive()` → 有报文就 `_process_frames()`（解码 + 越限判定）→ **反馈看门狗** → 距上次推送满 50 ms 就广播一次 → 睡 5 ms。

推送放在接收循环里、且不依赖是否收到报文，保证 MCU 不在线时界面的发送计数等也在刷新。

#### 5.5.6 急停与互锁

[emergency_stop(reason)](../backend/app/services/axle_manager.py#L756)：
1. 结束循环测试；置 `_is_emergency_locked = True`。
2. **不等 10 ms 循环，立即**同步发一帧"不使能、零转矩零转速、N 挡"。
3. 控制量保持安全值（之后 10 ms 循环也持续发安全帧）。
4. 写事件日志（手动 / 自动原因）。

互锁期间 [update_command](../backend/app/services/axle_manager.py#L724) 拒绝使能和任何非零控制量；[emergency_reset](../backend/app/services/axle_manager.py#L800) 只解除互锁，**控制量仍是安全值**，必须由操作员重新选择模式、使能、下发目标——这是防止"复位瞬间电机突然转起来"的关键不变量。

#### 5.5.6.1 平稳停机（与急停的区别）

[soft_stop()](../backend/app/services/axle_manager.py) 对应控制卡片上的"停机"按钮，用于**正常结束运行**：

1. 目标转速、转矩立即归零，**保持使能**，让控制器主动减速制动。
2. 启动 `_soft_stop_loop()`：每 50 ms 检查一次新鲜的 0x35B，实际转速绝对值 ≤ 30 rpm（`SOFT_STOP_SPEED_THRESHOLD_RPM`）即认为停稳，然后关闭使能、切 N 挡。
3. 30 s（`SOFT_STOP_TIMEOUT_SECONDS`）内没停稳也强制关闭使能（电机随后自由滑行），事件日志记为"超时"。
4. 未使能时调用，直接把目标归零并切 N 挡。

与急停的区别：**不进入互锁**，停完可直接重新操作；期间操作员下发新指令、急停、断开连接或启动循环测试都会终止停机流程（`_cancel_soft_stop_locked()`），以操作员的最新意图为准。遥测字段 `soft_stopping` 表示流程进行中，前端据此显示"减速停机中…"。

#### 5.5.7 自动安全监控（三种）

| 监控 | 函数 | 触发时机 | 判据 |
|---|---|---|---|
| 转速/转矩越限 | [_find_safety_violation](../backend/app/services/axle_manager.py#L862) | 每收到一帧 0x35B/0x35C | `|实际转速| > 阈值`、`|实际转矩| > 阈值`（绝对值，正反转都保护）、电机温度 > 阈值。只用 0.5 s（0x35B）/ 1 s（0x35C）内的新鲜数据 |
| 反馈中断看门狗 | [_find_feedback_timeout](../backend/app/services/axle_manager.py#L910) | 每 5 ms | 使能状态下，`现在 − max(使能时刻, 最近 0x35B 时刻) > feedback_timeout_ms` |
| 链路故障 | [_note_driver_error](../backend/app/services/axle_manager.py#L467) | 每次驱动调用异常 | 电机已使能或循环测试未结束时，同一收发源连续异常 ≥ 10 次或持续 ≥ 1 s；空闲时只置 `bus_warning`、不断开 |

前两种命中后都走 [_trip_safety](../backend/app/services/axle_manager.py#L940) → 记录 `AxleSafetyTrip`（前端据此弹窗）→ `emergency_stop(reason=...)`。
第三种走 `_schedule_link_failure` → **另起一个任务**执行 `_disconnect(failure_reason=...)`（不能在收发循环里直接断开，因为断开要取消收发循环自己）→ 记录 `link_error`。

为什么看门狗要以"使能时刻"为基准之一？如果只看"最近一次 0x35B"，刚使能时（还没收到过反馈）会立即误触发；如果只看"使能时刻"，后续反馈中断时检测不到。取两者较晚者正好覆盖两种情况。

#### 5.5.8 循环测试状态机

- [start_cycle_test](../backend/app/services/axle_manager.py#L559)：校验状态 → 深拷贝步骤（之后前端改表格不影响执行）→ 应用第一步（速度模式、使能、挡位、目标转速）→ 启动 `_cycle_loop`。
- [_cycle_loop](../backend/app/services/axle_manager.py#L651)：每 100 ms 用**单调时钟**扣减剩余时间（不受系统改时间、浏览器后台节流影响）；到时切下一步/下一圈；全部完成则 `completed` 并回到安全值。
- 暂停：立即写安全值，计时冻结；继续：重新应用当前步骤。
- **generation 机制**：每次开始/结束都 `_cycle_generation += 1`，旧的 `_cycle_loop` 任务醒来发现编号不一致就自行退出。这样即使取消信号没及时送达，也不会出现两个状态机同时控制。
- 循环测试持有控制权期间，手动控制接口和手动发 0x258 报文都被拒绝。

#### 5.5.9 SSE 广播

[_broadcast_telemetry](../backend/app/services/axle_manager.py#L1142)：
- 每个订阅者一个 `Queue(maxsize=30)`；满了就**丢最旧的**再放新的——界面要的是最新状态，不是完整历史。
- 同一次广播中，"带报文"和"不带报文"两种快照各只生成一次，多个订阅者共享。
- 报文监视缓冲区存的是轻量元组 `_FrameRecord`，只在生成快照时才转换成 `CanFrameItem`（每秒数百帧，避免高频构造模型的开销）。

#### 5.5.10 其他

- [_log_throttled](../backend/app/services/axle_manager.py#L449)：同一类告警 1 秒最多输出一次，并汇报被省略的次数，防止 10 ms 循环刷爆日志。
- [requires_close_confirmation](../backend/app/services/axle_manager.py#L206)：已连接且（已使能或循环测试未结束）时为真，桌面窗口关闭时据此决定是否弹确认。
- `get_axle_manager()` / `peek_axle_manager()`：前者懒加载创建单例；后者只查看、不创建（关闭窗口时用，避免为了判断而去加载 DLL）。

### 5.7 持久化与日志

### 5.8 桌面外壳 `desktop.py`

[main()](../backend/desktop.py#L195) 的流程：

```text
configure_logging()
单实例检查 acquire_single_instance()  ── 已有实例 → 把旧窗口切到前台，退出
create_app(serve_frontend=True)
绑定 127.0.0.1 的随机端口，在子线程运行 uvicorn（UvicornThread）
等待 uvicorn 启动完成（最多 15 s）
创建 PyWebView 窗口，注册 closing 事件 → make_closing_handler()
webview.start()  ← 主线程在这里运行界面，直到窗口关闭
关闭后：stop_server() 让 uvicorn 优雅退出 → 触发 lifespan → manager.shutdown() 发停机帧
```

- **为什么 uvicorn 在子线程**：PyWebView 要求界面事件循环必须在主线程。
- **随机端口**：避免和本机其他程序（例如别的 FastAPI 服务）抢 8000 端口。
- **单实例**：Windows 命名互斥量 `Local\ZhuChi-ElectricDriveAxle-EOL`，进程退出时系统自动释放。
- **关闭确认**：PyWebView 的 `closing` 事件在界面线程同步执行，处理函数返回 `False` 即取消关闭；弹框用 Win32 `MessageBoxW`，默认焦点在"否"。
- **`--smoke-test`**：不开窗口，只启动服务并请求 `/`、`/health`、`/status`、`/stream` 验证打包结果。

### 5.9 PLC 自动上电 / 下电

台架的 340 V 高压由西门子 S7-1500 PLC 控制。上位机通过以太网（python-snap7）读写 **DB40（dbPC）**，点表来自 PLC 工程师提供的 dbPC [DB40]，布局与 magmit 项目《高机点表(3)》的单个工位相同。代码分三层：

| 文件 | 职责 |
|---|---|
| [core/plc/points.py](../backend/app/core/plc/points.py) | 点表常量与字节编解码（纯函数）：`decode_station()` 解出 124 字节，`build_power_on_block()` 生成上电写入的 14 字节，`build_mes_block()` 生成上传 MES 的转速 / 温度 8 字节 |
| [core/plc/client.py](../backend/app/core/plc/client.py) | `SnapStationClient`（真实 PLC）与 `SimulatedStationClient`（本地仿真），同步接口，所有读写在锁内串行 |
| [services/plc_manager.py](../backend/app/services/plc_manager.py) | `PlcPowerManager`：连接、上电/下电编排、Safe 常驻联锁、心跳、转速 / 温度上传 MES，以及与 AxleManager 的双向联动 |

**点表（DB40 内偏移，基址 0）**

| 方向 | 点位 | 地址 | 本项目用法 |
|---|---|---|---|
| 写 | Heart | DBX0.0 | 每秒翻转（只用于显示） |
| 写 | Request_power | DBX0.1 | 1 上电 / 0 掉电 |
| 写 | Put_ProductType | DBW2 | 固定 1 |
| 写 | Request_voltage | DBW4 | 固定 340 |
| 写 | Result | DBW6 | 试车判定结果（1=OK 2=NG），手动判定或循环测试结束自动判定时写入、上传 MES；下次上电时清零 |
| 写 | Speed / Temp | DBD14 / DBD18 | REAL，电机实际转速 (rpm，0x35B `MCU_ActMotorSpd`，带正负) / 电机温度 (℃，0x35C `MCU_MotorTemp`)，只上传 MES，PLC 不参与判断 |
| 读 | Heart / Safe / Power_on / Connect | DBX62.0 / .1 / .2 / .3 | PLC 心跳、安全信号、上电完成、主接触器吸合 |
| 读 | Get_ProductType / Out_voltage / Out_current | DBW64 / 66 / 68 | 编号回传、电源输出 |
| 读 | Sn | DBB92 起 STRING[30] | 产品序列号（仅显示） |

**上电** [power_on()](../backend/app/services/plc_manager.py#L384)：检查 PLC 已连接 → 问 AxleManager 能否上电（[power_on_blocker()](../backend/app/services/axle_manager.py#L836)：循环测试中、电机使能中拒绝；急停互锁不阻止上电，因为互锁期间电机无法使能）→ 确认 Safe=1 → 在锁内"读字节 0 → 生成 14 字节（保留心跳位、Request_power=1、编号 1、340 V、Result 与未定义字节清零；不覆盖 Speed / Temp）→ 写回" → 每 0.2 s 轮询，最长 30 s 等 Power_on=1 且 Connect=1。超时、Safe 中途断开、被下电或急停中止时，后端自己把 Request_power 写回 0。回传编号不是 1 时上电仍算完成，但结果里给出提示。

**下电** [power_off()](../backend/app/services/plc_manager.py#L453)：先置"中止上电"标志（下电优先）→ 调 [disable_for_power_off()](../backend/app/services/axle_manager.py#L846)：结束循环测试和平稳停机、关闭使能，等 50 ms 让 10 ms 循环发出几帧安全帧 → Request_power=0 → 最长 5 s 确认 Power_on、Connect 都为 0；未确认返回 `partial` 并提示人工核查。

**常驻监视** [_monitor_step()](../backend/app/services/plc_manager.py#L323)（每 0.2 s）：一次读 124 字节刷新快照 → [_check_safety()](../backend/app/services/plc_manager.py#L340)：已请求上电或已通电但 Safe=0 时，复位 Request_power（每秒最多重试一次），并只触发一次 [external_safety_trip()](../backend/app/services/axle_manager.py#L862)（记录 `plc_safe` 停机事件 + 急停互锁），Safe 恢复后清除去重标记 → 每秒翻转上位机心跳；PLC 心跳 4 s 不跳变则显示"未跳变"（不参与任何判断）。

**转速 / 温度上传 MES** [_upload_mes()](../backend/app/services/plc_manager.py#L379)（随常驻监视每 0.2 s）：从 AxleManager 的 [mes_telemetry()](../backend/app/services/axle_manager.py#L849) 取实际转速与电机温度，与本次读回的 Speed / Temp 不同时才写（8 字节一次写入），值不变不产生通讯。CAN 未连接、或某项反馈超过 2 s 未更新时该项写 0，避免 PLC 拿到停在旧值的数据。

**反向联动** [cut_power_for_emergency()](../backend/app/services/plc_manager.py#L368)：AxleManager 急停（手动、越限、看门狗、Safe）或 CAN 链路故障时，通过 `add_emergency_listener` 在后台调用它，立即复位 Request_power，不等待其他操作，也不拖慢急停接口返回。

**其他约定**：
- 台架仍在供电时拒绝断开或切换 PLC 连接（否则失去 Safe 联锁）；程序退出时 lifespan 先让电驱桥发停机帧、释放 USBCAN，再复位 Request_power、断开 PLC。
- 连接参数（IP、机架、槽号、仿真）保存在 `plc_config.json`，默认 192.168.8.1 / 0 / 1。
- 仿真模式按时间推演 PLC：1.5 s 后上电完成、回传编号与电压，下电 0.5 s 后断开；页面上可用开关模拟 Safe 断开，用于演练。
- `GET /api/v1/plc/status` 返回后端内存快照，前端每 500 ms 轮询，不产生 PLC 通讯。

**PLC 通信监视**（[services/plc_traffic.py](../backend/app/services/plc_traffic.py)，移植自 magmit，联调用）：
- 写入：所有写操作都经过 `PlcPowerManager._update()`，它在锁内读-改-写后把**实际写入的字节**和**来源**（PLC 上电、下电、Safe 断开自动复位、急停联动、上电未完成复位、程序退出、心跳、MES 上传）交给 `PlcTrafficLog.record_write()`。只改一位时只记录那一位，避免每秒的心跳把"请求上电 = 0"也记一遍；上电写 14 字节时记录覆盖到的全部写区点位。
- 读取：常驻监视每 0.2 s 读完整个工位后调用 `sample()`，PLC 反馈区数值变化才记一条（旧值 → 新值）。复用这次读取，不额外产生 PLC 通讯；PLC 断开时清空基准，重新连上的第一次采样只建基准。
- 心跳与转速 / 温度记录属于高频记录，单独存放（最多 200 条），不会挤掉上电、Safe 变化等重要记录（最多 500 条）；只在内存中，程序重启后清空。
- 接口：`GET /plc/traffic/snapshot`（全部点位最新值）、`GET /plc/traffic/log?after_seq=`（增量拉取）、`DELETE /plc/traffic/log`。

**判定** `POST /test-records/judge`：取统计快照 → [write_result()](../backend/app/services/plc_manager.py#L387) 把 1/2 写入 Result（来源“试车判定”，通信监视里可见）→ 保存记录（序列号取 PLC 最近一次读到的 Sn）→ 清零统计。PLC 未连接或写入失败不阻止保存，记录标记 `plc_result_written=false`，返回信息里说明原因。循环测试执行中或正在自动判定时返回 409（`AxleManager.judge_blocker()`）。

**自动判定**：`start_cycle_test()` 先清零试车统计，只统计本轮循环。`_finish_cycle_locked()` 在循环正常跑完（`completed`）或异常中断（`error`，或 `abnormal=True` 的急停）时把 `cycle_test.auto_judge` 置为 `pending`，并在后台调用 `add_cycle_finished_listener()` 注册的联动；操作员终止、操作员下电、断开 CAN 不触发。`CycleAutoJudge.on_cycle_finished()`（在 `get_plc_manager()` 中注册）的流程：
1. `wait_motor_stopped()`：等实际转速 ≤ 30 rpm（最长 30 s），让减速过程中上报的故障码也计入本轮；
2. `evaluate_cycle()`：正常跑完且没有故障码、没有安全停机判合格，否则判 NG，备注写明原因；
3. `judge_test()` 写 Result 并保存记录；
4. 台架有供电时调用 `PlcPowerManager.power_off()`；
5. `report_auto_judge()` 把结论和下电结果写回 `cycle_test.auto_judge_result / auto_judge_message`，经遥测推送给界面。

`pending` 期间拒绝启动新一轮循环。

前端：[TestJudgeCard](../frontend/src/components/axle/TestJudgeCard.vue) 放在下线测试页，每秒拉取统计，判定前二次确认，循环执行中与自动判定期间禁用按钮；[CycleTestPanel](../frontend/src/components/axle/CycleTestPanel.vue) 显示自动判定进度与结论；[TestRecordsView](../frontend/src/views/TestRecordsView.vue)（`/records`）筛选、合格率汇总、导出。格式化函数在 [testRecordUtils.ts](../frontend/src/views/testRecordUtils.ts)（有单元测试）。

**设计思想：`telemetry` 是前端唯一的数据源**，内容就是后端推来的 `AxleTelemetry`。组件不自己保存业务状态，都从这里读。

| 成员 | 说明 |
|---|---|
| `telemetry` | 最新快照（SSE 每 50 ms 覆盖一次） |
| `isConnected / isEmergencyLocked / linkError` | 便捷的计算属性 |
| `historySeries` | 曲线数据：[recordHistory](../frontend/src/stores/useAxleStore.ts#L154) 每 100 ms 取一个点，只保留最近 30 s（约 300 点） |

| `connect / disconnect / sendCommand / ...` | 调接口，`loading`/`error` 统一管理 |
| `triggerEmergencyStop / resetEmergencyStop` | 成功后本地立即更新互锁标志；SSE 断开时才额外拉一次状态 |

`EventSource` 断线会**自动重连**，无需手写重连逻辑。

#### 顶部栏急停 [EmergencyStopButton.vue](../frontend/src/components/axle/EmergencyStopButton.vue)

#### 控制台 `/axle`

  - 每 200 ms 从 store 复制一次数据再渲染（降低高频刷新开销）。
  - [isFresh()](../frontend/src/components/axle/McuTelemetryCard.vue#L85)：0x35B 超过 500 ms、0x35A/0x35C 超过 1 s 未更新即视为"未知/无数据"，不显示陈旧值或默认值。

#### CAN 通讯 `/can`（[CanCommView.vue](../frontend/src/views/CanCommView.vue)）
连接参数、收发统计、原始报文监视。进入页面切换到"带报文"的 SSE 流，离开时切回。报文的过滤/聚合在 [canCommUtils.ts](../frontend/src/views/canCommUtils.ts) 的纯函数 `processFrames()` 里（有单元测试）：
- **ID 聚合**：按"方向 + ID"合并，显示最新一帧和累计帧数，按 ID 数值排序。聚合表由 `mergeFrameGroups()` 在页面生命周期内**持续累积**（按序号只处理新帧）：后端每次只推送最近 200 帧（约 0.9 s），若每次重新聚合，1 s 周期的 0x5EF 等低频报文会反复消失又出现。离开页面或点"清空"后重新统计。

## 7. 安全设计专题

### 7.1 分层原则

```text
第 1 层  台架硬件急停（切断控制器电源）   ← 最终保障，任何软件故障都有效
第 2 层  MCU 自身保护（VCU 节点丢失故障 46、过流、过温等）
第 3 层  上位机软件保护（本软件）        ← 本文档描述的内容
```

**上位机软件急停不是安全功能的替代品**：程序崩溃、被强制结束、电脑断电时它什么也做不了，只能依赖第 1、2 层。

### 7.2 失效场景对照表

| 场景 | 谁发现 | 反应时间 | 结果 |
|---|---|---|---|
| 操作员按急停 | 操作员 | 立即发一帧 | 互锁，安全帧持续发送 |
| 转速/转矩超阈值 | 接收循环（每帧 0x35B） | ≈ 一帧（10 ms 级） | 自动急停 + 弹窗 + 事件日志 |
| 电机温度超阈值 | 接收循环（每帧 0x35C） | ≈ 100 ms 级 | 同上 |
| 使能中 MCU 掉线 / CAN 线断 | 反馈看门狗 | 阈值（默认 500 ms）+ 5 ms | 同上 |
| USBCAN 被拔出（测试进行中） | 链路故障检测 | ≤ 1 s（或连续 10 次异常） | 自动断开、循环测试置错误、右下角常驻提示 + 事件日志 |
| 控制器未上电 / USBCAN 被拔出（空闲） | 链路故障检测 | 首次异常 | 保持连接，提示“CAN 总线无应答”；恢复后自动消除。期间若使能或启动循环，下一次异常即自动断开 |
| 操作员点"停机" | 程序 | 立即归零；转速 ≤ 30 rpm 后关使能（最长 30 s） | 控制器减速到停，不互锁 |
| 操作员断开 / 关窗口 | 程序 | ≤ 200 ms | 先发 2 帧停机帧再释放；运行中关窗需确认 |
| 程序崩溃 / 被结束 | MCU（停止收到 VCU_11） | 取决于 MCU 标定 | MCU 报故障 46 并停机（需在台架实测确认） |
| 两个程序同时控制 | 单实例互斥量 | 启动时 | 第二个实例不启动 |
| PLC 安全回路断开（Safe=0） | PLC 常驻监视（0.2 s） | ≤ 0.2 s | 复位上电请求切断高压 + 自动急停 + 弹窗 + 事件日志 |
| 急停 / CAN 链路故障时仍在供电 | 急停联动 | 立即（后台执行） | 复位 PLC 上电请求，切断高压 |
| 上电 30 s 无反馈 | 上电流程 | 30 s | 复位上电请求，提示超时 |

### 7.3 关键不变量（修改代码时不要破坏）

1. 急停互锁期间，后端拒绝使能和任何非零控制量。
2. 解除互锁后，控制量仍为安全值，绝不自动恢复。
3. 安全判定只用"新鲜"反馈，不用默认值或断线前的旧值。
4. 断开/退出时 VCU_11 的 Life 保持连续，最后几帧是安全帧。
5. 循环测试执行期间，手动控制与手动 0x258 报文一律拒绝。
6. 安全相关的校验一定在后端做，前端校验只是提示。
7. 任何急停、Safe 断开、上电失败都要把 Request_power 复位为 0；电机使能中禁止 PLC 上电；急停互锁中允许上电（互锁期间电机无法使能）。

## 8. 关键流程时序

### 8.1 连接

```text
界面  ──POST /connect──▶ 路由 ──▶ manager.connect()
                                   ├─ [生命周期锁] 已连接? → 先 _disconnect()
                                   ├─ [状态锁] open_device → open_channel(×n) ──失败──▶ 回滚并抛错 → 500
                                   ├─ _connected = True
                                   └─ create_task(_tx_loop), create_task(_rx_loop)
界面  ◀── 200 ── ; store.refreshStatus(); startSse()
```

### 8.2 自动越限停机

```text
MCU ─0x35B─▶ _rx_loop ─▶ _process_frames ─▶ decode ─▶ _evaluate_safety()
                                                       └─ 超阈值 → _trip_safety()
                                                            ├─ 记录 AxleSafetyTrip(trip_id+1)
                                                            └─ emergency_stop(reason)
                                                                 ├─ 互锁 + 立即发安全帧
                                                                 └─ events.log: 紧急停机: 自动安全停机 — ...
下一次广播 ─SSE─▶ store.telemetry.safety.last_trip 变化 ─▶ SafetyTripDialog 弹出
```

### 8.3 USBCAN 拔出

```text
_tx_loop: transmit 抛 CanDriverError（0.5 s 超时或句柄失效）
   └─ _note_driver_error("tx0") 累计 → 达到 10 次或 1 s
        └─ _schedule_link_failure(reason) → 新任务 _handle_link_failure
              └─ [生命周期锁] _disconnect(failure_reason)  // 尽力发停机帧，释放设备
                    └─ link_error = reason; events.log 记录
SSE ─▶ AppLayout 在右下角弹出常驻提示（重连成功后自动收起）
```

## 12. 排障手册

**第一步永远是看日志**：`%APPDATA%\electric-drive-axle\logs\events.log`（发生了什么）和 `app.log`（详细原因）。

| 现象 | 可能原因 | 怎么查 / 怎么办 |
|---|---|---|
| 双击 EXE 没窗口 / 白屏 | 缺 WebView2；已有实例在运行 | 安装 WebView2；看任务栏是否已有窗口 |
| CAN 页红色提示"驱动加载失败" | `zlgcan.dll` 或其依赖加载失败 | 提示里有路径和原因；装 VC++ 运行库 / USBCAN 驱动 |
| 连接时报"打开 ZLG 设备失败" | 设备没插、被其他软件占用、设备类型/索引选错 | 关闭 ZLG 官方工具等占用软件；核对设备型号 |
| 已连接但 RX 一直为 0 | 波特率不一致、MCU 未上电、终端电阻缺失 | 发送错误数是否在涨（无应答）；量终端电阻 |
| 发送错误数持续增加 | 总线无应答（MCU 未上电/接线错误/缺终端电阻） | 同上 |
| 使能后约 0.5 s 自动急停，提示"反馈中断" | 收不到 0x35B | MCU 是否在发；空载调试无 MCU 时可临时关闭安全监控 |
| 加速时自动急停，提示转矩越限 | 转矩阈值（默认 10 Nm）太低 | 按测试规范调整阈值 |
| 提示"CAN 硬件链路中断" | USBCAN 拔出、USB 供电不稳、驱动卡死 | 检查 USB 线与供电；重新连接 |
| 母线电压未上高压时显示二十几伏 | MCU 采样零漂或母线残余电压（非上位机问题） | 万用表实测母线电压 |
| PLC 上电提示"安全回路未闭合 (Safe=0)" | 现场安全条件未满足（急停按钮、门禁等） | 排查 PLC 安全回路后重试 |
| PLC 上电超时 | PLC 30 s 内未置位上电完成 / 主接触器 | 看"台架供电"页底部的 PLC 通信监视：确认"请求上电 = 1"已写出，再看 PLC 侧哪一项没有变化；在 PLC 侧核对 DB40.DBX62.2、62.3 |
| PLC 上电提示"电机仍处于使能状态" | 上电前要求电机不使能 | 先在控制台停机并关闭使能 |
| 顶部栏出现"供电故障" | PLC 通信中断，或 Safe 断开，或已请求上电但未完成 | 到"台架供电"页查看原因；必要时下电重试 |
| 操作按钮全部灰色 | 未连接 / 急停互锁 / 循环测试占用 | 看控制台提示条；互锁需"解除急停互锁" |

## 13. 已知限制与后续建议

- **无按台测试记录**：没有序列号录入、合格判定和报告导出。如产线需要，可作为新功能开发。
- **未上高压时母线电压显示非零**：可增加"低于阈值显示未上高压"。
- **报文监视最多保留 500 帧**，界面显示最近 200 帧；它是诊断工具，不是总线记录仪。
- **软件急停依赖程序存活**：见 7.1，必须有硬件急停。
- **前端无组件级自动化测试**：界面改动需人工验证。

## 14. 术语表

| 术语 | 含义 |
|---|---|
| VCU | 整车控制器。台架上由本上位机扮演 |
| MCU | 电机控制器（被测对象的控制器） |
| VCU_11 | 上位机发给 MCU 的控制报文，ID 0x258 |
| EOL | End of Line，下线测试 |
| Life 计数器 | 每帧递增的 4 位计数，用于判断对方是否卡死/丢帧 |
| 使能 | 允许 MCU 驱动电机输出 |
| 互锁 | 急停后禁止重新使能，直到操作员显式复位 |
| 新鲜度 | 反馈数据距最近一次成功接收的时间是否在阈值内 |
| 看门狗 | 周期检查"某事是否按时发生"，超时就采取保护动作 |
| SSE | 服务器单向实时推送技术 |
| 单例 | 整个进程只存在一个实例的对象（AxleManager） |
| 协程 / 任务 | Python 异步函数及其调度单位 |
| SJA1000 | 经典 CAN 控制器芯片，USBCAN2 用它的 Timing0/1 寄存器设定波特率 |
| PyInstaller | 把 Python 程序打包成 EXE 的工具 |
| PyWebView | 用系统浏览器内核显示网页的原生窗口库 |
